# GET-параметры проекта и правила robots.txt

Дата проверки: 02.10.2026. Источник — текущий локальный код проекта, включая установленные Filament и Livewire. Сохранённые настройки robots.txt и конфигурация серверов в рамках этой проверки не изменялись и не проверялись.

Готовый текст: [robots-query-parameters.txt](robots-query-parameters.txt). Это строгий вариант запрета обхода всех найденных фильтров, сортировки и пагинации; служебные разделы закрыты целиком. Правила разделены на группы `*`, `Googlebot`, `Googlebot-Image` и `Yandex`. Для Яндекса добавлена очистка рекламных меток через `Clean-param`; остальные группы запрещают обход URL с такими метками. Параметры версии CSS/JS не запрещаются.

## Поиск с картой: `/search`

| Параметр | Назначение / значения |
| --- | --- |
| `q` | Текст поиска по организациям. |
| `r` | ID региона. |
| `d` | ID выбранной территории внутри региона: район или более глубокий уровень. |
| `t` | Старый параметр территории; читается для совместимости, в новых ссылках заменён на `r` и `d`. |
| `cat` | ID категорий организаций через запятую. |
| `res` | ID видов ресурсов через запятую. |
| `work` | Виды работ: `all`, `both`, `smr`, `pir`; `all` обычно отсутствует в URL. |
| `seg` | Сегмент: `b2b`, `b2c`, `both`. |
| `sort` | Сортировка: `name_asc`, `rating_best`; значение по умолчанию `rating_best` обычно отсутствует в URL. |
| `page` | Номер страницы результатов; первая страница обычно без параметра. |

Параметры формируются и читаются в [шаблоне поиска](../resources/views/search/index.blade.php), методы `buildQueryParams()` и `initFromQueryParams()`, строки 676–709. На сервере `SearchController` подготавливает данные; фильтрация и работа с URL выполняются в JavaScript.

## Каталог и направления

Маршруты: `/catalog`, `/catalog/{slug}`, `/directions`, `/directions/{slug}`.

| Параметр | Назначение / значения |
| --- | --- |
| `organization_type` | ID категории организации. Обрабатывается, когда категория не зафиксирована в пути `/catalog/{slug}`; также используется в направлениях. |
| `direction_id` | ID направления. Обрабатывается, когда направление не зафиксировано в пути `/directions/{slug}`; также используется в каталоге. |
| `rating_id` | ID рейтинга. |
| `territory_path[0]`, `territory_path[1]`, … | Массив ID последовательных территорий: регион → район → МО → последующие уровни. Сервер рассматривает индексы 0–11. Корневое имя параметра — `territory_path`. |
| `territory_id` | Старый одиночный ID территории; используется, если `territory_path` не передан массивом. |
| `sort` | `name` или `rating`, по умолчанию `name`. |
| `page` | Серверная пагинация, по 12 организаций. |

Источники: [DirectoryController](../app/Http/Controllers/DirectoryController.php), чтение фильтров в `renderDirectory()` и `territorySelection()`, пагинация через `paginate(12)->withQueryString()`; [каскадный фильтр](../resources/views/directory/partials/territory-filter.blade.php).

`{slug}` — сегмент пути, а не GET-параметр. Страницы категорий и направлений без query string остаются доступны при применении подготовленных правил.

Для массива URL обычно выглядит так:

```text
/catalog?territory_path%5B0%5D=10&territory_path%5B1%5D=20
```

В правилах предусмотрены и кодированные `%5B`, и буквальные `[`; запрет действует на любой индекс массива и на любую позицию параметра в query string.

| Маршрут | GET-параметры | Назначение |
| --- | --- | --- |
| `/api/geo/tree` | `parent_id` | Дочерние территории указанного родителя. |
| `/api/geo/map-features` | `level`, `region_id` | Уровень геообъектов и ID региона для отбора геометрии карты. |
| `/api/geo/units/{id}` | Нет собственных query-параметров | `id` передаётся в пути. |
| `/api/user` | Нет собственных query-параметров | Авторизованный пользователь. |

Источник: [GeoController](../app/Http/Controllers/Api/GeoController.php), строки 15, 36–37; [маршруты API](../routes/api.php). Поиск обращается к `/api/geo/map-features?region_id=…`.

В готовом тексте API закрыт целиком правилами `/api$`, `/api?` и `/api/`. Это также запрещает роботу получать геометрию при отрисовке карты на `/search`. Если получение данных карты роботом требуется, эти три правила следует убрать и отдельно определить политику обхода API.

## Админка и личный кабинет: `/dashboard`

Собственный параметр проекта: `parent_id` — переход между уровнями геообъектов. В Livewire свойство называется `parentId`, но URL использует именно `parent_id`.

Источник: [ListGeoUnits](../app/Filament/Resources/GeoUnitResource/Pages/ListGeoUnits.php), строки 19–29; ссылки формируются также в `GeoUnitResource`.

Установленная версия Filament дополнительно поддерживает следующие query-параметры страниц админки:

| Параметры | Назначение |
| --- | --- |
| `search`, `sort`, `filters[...]`, `grouping` | Поиск, сортировка, фильтры и группировка таблицы. |
| `page` | Пагинация таблицы через Livewire. |
| `tab`, `reordering` | Активная вкладка и режим изменения порядка. |
| `action`, `actionArguments[...]`, `actionContext[...]` | Открытие действия с аргументами и контекстом. |
| `tableAction`, `tableActionRecord`, `tableActionArguments[...]` | Открытие действия над записью таблицы. |

Источники в установленном vendor: `filament/filament/src/Resources/Pages/ListRecords.php`, `filament/actions/src/Concerns/InteractsWithActions.php`, `livewire/livewire/src/Features/SupportPagination/HandlesPagination.php`. Наличие поддержки не означает, что каждый параметр используется каждым экраном.

`relation` поддерживается базовыми страницами Filament для relation managers, но собственные relation managers в текущем `app/Filament` не найдены; это не отдельный подтверждённый фильтр проекта. `tableRecordsPerPage` сохраняется в сессии, отдельного GET-параметра `perPage` в проверенном коде нет.

Для всех экранов достаточно:

```text
Disallow: /dashboard$
Disallow: /dashboard?
Disallow: /dashboard/
```

Правила закрывают корень раздела, корень с query string и вложенные страницы со всеми их query-параметрами. Отдельные глобальные запреты `action`, `filters`, `search` и других параметров админки не нужны.

## Прочие места и технические параметры

У главной страницы, `/info/{slug}`, `/organizations/{slug}`, `/login`, `/register`, sitemap и экспорта организаций собственных GET-фильтров не найдено. `/agent/{slug}` и `/agents/{slug}` — редиректы на карточку организации. Параметры `slug`, `part`, `record`, `contractorTariff` в объявлениях маршрутов или ссылках на редактирование соответствуют сегментам пути, а не автоматически query string.

Поля авторизации, регистрации, заявок и отзывов отправляются POST-запросами и не включены в список GET-параметров.

В ресурсах фреймворков используются параметры версии:

| Параметр | Где | Решение для robots.txt |
| --- | --- | --- |
| `id` | JavaScript Livewire, `livewire.js?id=…` | Не запрещать глобально: параметр версии JS. |
| `v` | CSS, JS и Alpine-компоненты Filament | Не запрещать глобально: параметр версии ресурсов. |

Источники: `vendor/livewire/livewire/src/Mechanisms/FrontendAssets/FrontendAssets.php`, `vendor/filament/support/src/Assets/{Js,Css,AlpineComponent}.php`.

`lang`, `apikey` в подключении Яндекс Карт; `v` в ссылках YouTube; `family`, `display` в ссылке Google/Bunny Fonts относятся к внешним доменам. robots.txt этого проекта на них не действует.

`utm_*`, `yclid`, `gclid`, `fbclid` не формируются и не используются как фильтры в проверенной логике проекта. Упоминания UTM и `fbclid` в `ValidateSignature` закомментированы. Такие метки могут приходить из внешних рекламных ссылок, но не входят в подтверждённые параметры приложения. В готовые правила они добавлены отдельно как профилактика появления дублей; это не утверждение, что такие URL обнаружены на сайте. Произвольные URL, сохранённые редакторами в БД, не исследовались; перечень описывает обработку и генерацию параметров кодом.

Итого: 15 уникальных корневых имён параметров публичных страниц и ещё 3 параметра API (`parent_id`, `level`, `region_id`). `parent_id` также используется в админке. Параметры фреймворков и внешних сервисов перечислены отдельно.

## Как применять готовые правила

В [готовом тексте](robots-query-parameters.txt) для каждого скалярного фильтра есть два правила, например:

```text
Disallow: /*?q=
Disallow: /*?*&q=
```

Они закрывают параметр первым в строке запроса и после других параметров. Имя ограничено разделителем и знаком `=`, поэтому правило для `q` не запрещает случайно `faq` или `utm_q`. `*` в robots.txt — wildcard, `?` — буквальный разделитель query string; это не регулярное выражение. Синтаксис wildcard и `$` описан в [спецификации Google](https://developers.google.com/crawling/docs/robots-txt/robots-txt-spec).

Готовый файл содержит четыре самостоятельные группы и один абсолютный URL sitemap для основного домена. Общие запреты полностью повторены в каждой группе: нельзя рассчитывать на наследование правил `*` отдельными группами роботов. При добавлении в существующий robots.txt нужно сохранить его необходимые правила и согласовать уже существующие группы этих же роботов.

### Группы роботов и Clean-param

| Группа | Фильтры, сортировка, пагинация; админка и API | Рекламные и аналитические параметры |
| --- | --- | --- |
| `*` | `Disallow` | `Disallow` для каждого точного имени параметра. |
| `Googlebot` | Полный собственный набор `Disallow`. | `Disallow`; Google не поддерживает `Clean-param`. |
| `Googlebot-Image` | Полный собственный набор `Disallow`. | `Disallow`; изображения и ресурсы без запрещённых параметров остаются доступны. |
| `Yandex` | Полный собственный набор `Disallow`. | Только `Clean-param`, без запрета обхода этих же меток. |

Поддерживаемые поля robots.txt и выбор наиболее подходящей группы описаны в [документации Google](https://developers.google.com/crawling/docs/robots-txt/robots-txt-spec). Синтаксис и назначение `Clean-param` — в [документации Яндекса](https://yandex.ru/support/webmaster/ru/robot-workings/clean-param).

В группу Яндекса добавлены:

```text
Clean-param: utm_source&utm_medium&utm_campaign&utm_term&utm_content&utm_id&utm_source_platform&utm_creative_format&utm_marketing_tactic
Clean-param: yclid&ysclid&ymclid&etext&yadclid&yadordid&clid&erid&_openstat&ym_debug
Clean-param: gclid&dclid&gbraid&wbraid&fbclid&msclkid&srsltid
```

Отсутствие пути означает действие на всём сайте. Имена перечисляются через `&`, wildcard `utm_*` для имени параметра не используется. Каждая строка укладывается в ограничение Яндекса 500 символов. Некоторые обычные метки, включая часть UTM и `ysclid`, Яндекс может очищать автоматически; явное перечисление фиксирует желаемую политику.

Фильтры `q`, `r`, `d`, `cat`, `res`, `organization_type`, `direction_id`, `rating_id`, территории и виды работ меняют содержимое результата. `page` меняет набор организаций, `sort` меняет порядок и при пагинации также состав страницы. Поэтому они остаются значимыми параметрами и не добавлены в `Clean-param`. `id` и `v` версии ресурсов также не очищаются.

Для одного и того же URL `Disallow` имеет приоритет над `Clean-param`. Поэтому для рекламных меток Яндекса запреты из общих и Google-групп не повторены: Яндекс применяет свою отдельную группу и может свести URL с меткой к адресу без неё. Если URL одновременно содержит фильтр и рекламную метку, запрет фильтра сохраняется.

### Пагинация

Подготовлен строгий вариант, включающий:

```text
Disallow: /*?page=
Disallow: /*?*&page=
```

Однако [PublicSeo](../app/Support/PublicSeo.php) сейчас выставляет `index, follow` для `/search`, когда единственный GET-параметр — корректный `page`. Для каталогов и направлений query string, включая одиночный `page`, получает `noindex, follow` и canonical на URL без query string. Таким образом, запрет `page` дополнительно закроет обход пагинации поиска, которая сейчас разрешена к индексации.

Если требуется сохранить обход пагинации, уберите эти две строки из каждой из четырёх групп готового текста. Сочетания `page` с фильтрами или сортировкой останутся закрыты остальными правилами. Каталогам и направлениям для индексации самой пагинации потребовалась бы отдельная корректировка текущей SEO-логики.

### Обход и индексация

`Disallow` запрещает обход. Он не гарантирует удаление уже известных URL из выдачи. При запрете обхода Google не сможет прочитать существующий `noindex` страницы. Это различие следует учитывать, если цель — удаление URL из индекса, а не ограничение обхода. [Документация Google о noindex](https://developers.google.com/search/docs/crawling-indexing/block-indexing).

Нельзя заменять подготовленные правила общим `Disallow: /*?`: он также закроет версии CSS/JS и любые другие URL с query string.

### Где хранится robots.txt проекта

В проекте robots.txt формируется маршрутом [routes/web.php](../routes/web.php) из сохранённого поля `robots` настроек SEO ([SeoSettings](../app/Support/SeoSettings.php)). Подготовленный текст предназначен для этого поля. Создание `public/robots.txt` может переключить обслуживание на статический файл и обойти настройки приложения.

Этот документ и `.txt` — подготовленные материалы. Их включение в релиз само по себе не меняет сохранённое поле robots.txt в SEO-настройках.
