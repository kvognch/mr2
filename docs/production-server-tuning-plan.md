# План проверки и настройки production-сервера MR2

Дата аудита: 29 сентября 2026 года
Область: конфигурация production-хоста, веб-стека и баз данных. Аудит выполнен в режиме чтения; конфигурации и службы не менялись.

## Текущий профиль

- ОС: Ubuntu 24.04.2 LTS.
- Ресурсы: 2 vCPU, 2 ГБ RAM, swap отсутствует. На момент снимка было доступно около 1 ГБ RAM; load average — `0.00, 0.03, 0.01`. Раздел `/` — 29 ГБ, занято около 17 ГБ, свободно около 13 ГБ.
- Веб-схема: Nginx принимает запросы и проксирует production и dev на один Apache по localhost. Оба сайта используют общий экземпляр Apache.
- Nginx 1.26.3: `worker_processes auto`, `worker_connections 1024`, `keepalive_timeout 65`, `proxy_read_timeout 120s`, `client_max_body_size 100m`. По текущему снимку менять эти значения не требуется.
- Apache 2.4.58: MPM `prefork`, загружены `mod_php` и `mpm_itk`. Для обоих сайтов настроены `SetHandler application/x-httpd-php` и `AssignUserId`. `MaxRequestWorkers=150`, `MaxConnectionsPerChild=0`, `StartServers=5`, `MinSpareServers=5`, `MaxSpareServers=10`.
- В Apache error log обнаружены три события достижения `MaxRequestWorkers` — 22, 25 и 29 сентября. Последнее событие совпало по времени со всплеском около 119 запросов за минуту на dev. Совпадение указывает на возможную связь, но само по себе не доказывает причину.
- PHP 8.3 обслуживает сайт через Apache `mod_php`, а не через PHP-FPM. Поэтому `pm.max_children=5` у работающего PHP-FPM-пула не ограничивает параллелизм запросов MR2. Глобальный `memory_limit=128M`; middleware Filament приложения повышает лимит только для административных запросов до `256M`. В настройках сайтов `max_execution_time=120`, `max_input_vars=10000`, `post_max_size=100M`, `upload_max_filesize=100M`.
- PostgreSQL 14.17; apt-кандидат на хосте — 14.24. Production-база около 72 МБ. Текущие значения: `shared_buffers≈150 МБ`, `work_mem=4 МБ`, `maintenance_work_mem≈30 МБ`, `effective_cache_size≈600 МБ`, `max_connections=100`. В накопленной статистике попадания в кэш — около 99,2%, временных файлов — 0.
- На этом же хосте работают MySQL, FASTPANEL, почтовые, Redis и Memcached-службы. PSS процесса MySQL — около 189 МБ; размер InnoDB buffer pool — 128 МБ. Максимум одновременно использованных MySQL-подключений в доступной статистике — 3.
- В проверенных за последние семь дней сообщениях ядра OOM-событий не найдено. Это не исключает коротких пиков памяти; снятый снимок нагрузки не заменяет наблюдение во время реального пика.

## План действий

### 1. Снизить влияние dev на production

Production и dev делят один Apache и общие ресурсы хоста. Ограничить доступ к dev HTTP-аутентификацией или списком разрешённых IP. Если публичный доступ необходим — настроить отдельное ограничение частоты запросов для dev-виртуального хоста в Nginx.

После ограничения проверить, повторяются ли события `reached MaxRequestWorkers`. Это самый малорисковый первый шаг: он уменьшает постороннюю конкуренцию за Apache, не ограничивая пользователей production.

### 2. Измерить Apache перед изменением лимитов

Включить `mod_status` с доступом только с localhost или из доверенной административной сети. Во время пиков собирать:

- `BusyWorkers` и `IdleWorkers`;
- число процессов Apache и PSS активных дочерних процессов;
- частоту и длительность запросов, долю ошибок 5xx и события `MaxRequestWorkers`;
- потребление памяти хостом и соседними службами.

Затем рассчитывать `MaxRequestWorkers` исходя из измеренного PSS активного PHP-процесса, размера RAM и резерва для PostgreSQL, MySQL, панели, почты, ОС и файлового кэша. Не повышать текущий лимит 150 только потому, что Apache пишет `consider raising`; не снижать его произвольно до получения метрик, иначе очередь запросов может вырасти.

`MaxConnectionsPerChild=0` означает, что дочерние процессы не завершаются по числу обслуженных соединений. Если измерения покажут рост PSS процесса со временем, испытать ограничение порядка 500–1000 соединений на процесс. Не считать это самостоятельным решением насыщения Apache.

### 3. Оставить текущий PHP memory limit адресным

Сохранить глобальный `memory_limit=128M` и повышение до `256M` только для административных запросов Filament. Не поднимать глобальное значение до 256M: при `prefork` дополнительные PHP-процессы могут одновременно потреблять больше памяти.

Проверить медленные веб-маршруты с текущим `max_execution_time=120` и `proxy_read_timeout=120s`. После определения долгих операций установить для обычных HTTP-запросов более короткий предел (например, 60–90 секунд), если это совместимо с приложением. Длительные импорты, экспорты и другие фоновые задачи выполнять через очередь или CLI. Таймаут Nginx должен быть согласован с лимитом PHP, чтобы не обрывать намеренно длительные запросы раньше приложения.

### 4. Рассмотреть переход `mod_php` → PHP-FPM отдельно от срочных мер

Текущие `mod_php` и `mpm_itk` связаны с режимом `prefork` и изоляцией пользователей в Apache. Нельзя просто переключить MPM на `event`: сначала нужно настроить через FASTPANEL PHP-FPM-пулы с корректными пользователями и правами, затем проверить production-подобную нагрузку на dev. После этого оценить переход Apache на `event` и отключение `mod_php`/`mpm_itk`, если панель поддерживает такую схему.

При миграции `pm.max_children` назначать отдельно для каждого пула по измеренному потреблению памяти и фактической параллельности. Нынешнее значение `5` относится к активному FPM-пулу, но не задаёт лимит текущих запросов MR2.

### 5. Обновить PostgreSQL

1. Подготовить и проверить резервную копию production-базы.
2. В окно обслуживания обновить minor-версию PostgreSQL с 14.17 до доступной 14.24, затем проверить подключение приложения, миграции и основные маршруты.
3. До окончания поддержки PostgreSQL 14 (12 ноября 2026 года) проверить совместимость и подготовить переход на поддерживаемую major-версию — 17 или 18. Major-обновление сначала репетировать на копии базы, включая проверку расширений и плана возврата.

### 6. Не менять сейчас параметры памяти PostgreSQL и Nginx

Размер базы, высокая доля попаданий в кэш и отсутствие временных файлов не дают оснований увеличивать PostgreSQL `shared_buffers` или `work_mem`. Хост обслуживает несколько других служб, поэтому ориентир в 25% RAM для выделенного сервера БД здесь неприменим автоматически. Не повышать `max_connections` до лимита Apache: сначала согласовать HTTP-конкурентность с бюджетом RAM и наблюдаемым числом соединений PostgreSQL. PgBouncer рассматривать только при подтверждённой проблеме с числом или стоимостью подключений.

Параметры Nginx, MySQL, PostgreSQL I/O и файловой системы оставить без изменений, пока метрики не покажут соответствующее узкое место. Не отключать MySQL или кэширующие службы без выяснения, какие функции FASTPANEL и других сайтов от них зависят.

### 7. Рассмотреть запас по памяти

2 ГБ RAM достаточно для текущего спокойного снимка, но запас ограничен при нескольких тяжёлых запросах Filament и общем размещении production, dev, БД, панели и почты. Если после ограничения dev и настройки конкуренции пики остаются, рассмотреть увеличение RAM до 4 ГБ; текущий срез не указывает на необходимость добавлять CPU.

Как дополнительную защиту от краткого всплеска можно рассмотреть 1–2 ГБ swap при наличии подходящего дискового режима. Swap не считать рабочим запасом памяти: постоянный обмен со swap ухудшит время ответа и должен вести к поиску причины либо увеличению RAM.

## Порядок внедрения и проверка

1. Ограничить dev и включить защищённый мониторинг Apache.
2. Собрать метрики во время пиков; по ним определить безопасный `MaxRequestWorkers` и необходимость переработки таймаутов.
3. Отдельным изменением обновить PostgreSQL 14 до 14.24 после проверки резервной копии.
4. На dev проверить схему PHP-FPM и изоляцию пользователей; только после успешной проверки планировать переключение MPM.
5. После каждого изменения проверить публичные production/dev маршруты, логи Apache и приложения, потребление RAM, соединения PostgreSQL и повторяемость ошибок 5xx.

Конфиги FASTPANEL не редактировать напрямую, если панель может их перегенерировать. Использовать настройки панели или предусмотренные пользовательские include-файлы.
